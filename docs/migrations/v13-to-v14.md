# Migration guide: Secretlint v13 to v14

Most users do not need to change anything. Existing `.secretlintrc` files keep working, and the rule ids do not change. Node.js 22 or later is still supported.

This guide lists what changes for each kind of user.

- [Everyone](#everyone)
- [Command line users](#command-line-users)
- [Users of custom formatters and the JSON output](#users-of-custom-formatters-and-the-json-output)
- [Users of the API](#users-of-the-api)
- [Rule authors](#rule-authors)

## Everyone

### Remove the rule packages

**The packages are gone, but their rule ids stay.**
Keep using the same ids in `.secretlintrc.json`.
This configuration works in v14 without installing any rule package:

```json
{
  "rules": [
    { "id": "@secretlint/secretlint-rule-preset-recommend" }
  ]
}
```

The official rules and the presets are part of `@secretlint/core`, so the rule packages that you installed are no longer used.
Remove them to avoid installing packages that are not used:

```sh
npm uninstall @secretlint/secretlint-rule-preset-recommend
```

If you installed other official rule packages, this command removes all of them (a package that is not installed is skipped):

```sh
npm uninstall @secretlint/secretlint-rule-1password @secretlint/secretlint-rule-anthropic @secretlint/secretlint-rule-aws @secretlint/secretlint-rule-azure @secretlint/secretlint-rule-basicauth @secretlint/secretlint-rule-cloudflare @secretlint/secretlint-rule-database-connection-string @secretlint/secretlint-rule-databricks @secretlint/secretlint-rule-docker @secretlint/secretlint-rule-figma @secretlint/secretlint-rule-filter-comments @secretlint/secretlint-rule-gcp @secretlint/secretlint-rule-github @secretlint/secretlint-rule-gitlab @secretlint/secretlint-rule-grafana @secretlint/secretlint-rule-groq @secretlint/secretlint-rule-hashicorp-vault @secretlint/secretlint-rule-huggingface @secretlint/secretlint-rule-linear @secretlint/secretlint-rule-notion @secretlint/secretlint-rule-npm @secretlint/secretlint-rule-openai @secretlint/secretlint-rule-pattern @secretlint/secretlint-rule-preset-canary @secretlint/secretlint-rule-preset-recommend @secretlint/secretlint-rule-privatekey @secretlint/secretlint-rule-sendgrid @secretlint/secretlint-rule-shopify @secretlint/secretlint-rule-slack @secretlint/secretlint-rule-stripe @secretlint/secretlint-rule-tailscale @secretlint/secretlint-rule-vercel
```

### The official rules are built in

You do not need to install `@secretlint/secretlint-rule-preset-recommend` or another official rule package.

```sh
# v13
npm install secretlint @secretlint/secretlint-rule-preset-recommend --save-dev
# v14
npm install secretlint --save-dev
```

- The rule ids in `.secretlintrc` do not change. `@secretlint/secretlint-rule-preset-recommend` and `@secretlint/secretlint-rule-aws` still work.
- An official rule id is always resolved from `@secretlint/core`, even when an old package of the same name is installed. The rules always have the same version as `secretlint`.
- The official rule packages and the preset packages are no longer published. If you keep them, they are not loaded.
- The documentation of each rule moves to [docs/rules](https://github.com/secretlint/secretlint/tree/HEAD/docs/rules).

These rules are still separate packages: `@secretlint/secretlint-rule-no-dotenv`, `@secretlint/secretlint-rule-no-homedir`, `@secretlint/secretlint-rule-no-k8s-kind-secret`, and `@secretlint/secretlint-rule-secp256k1-privatekey`.

### Secretlint runs the recommended rules when there is no configuration

When no configuration file is found from the current directory up to the root, and neither `--secretlintrc` nor `--secretlintrcJSON` is given, Secretlint runs `@secretlint/secretlint-rule-preset-recommend`.
In v13, it stopped with `Error: secretlint config is not found` and exit status 2.

A broken configuration file is still an error.

### `enableIDScanRule` of the aws rule must be a boolean

```json
{ "id": "@secretlint/secretlint-rule-aws", "options": { "enableIDScanRule": true } }
```

A string such as `"true"` stops Secretlint with an error:

```
The option "enableIDScanRule" of the rule "@secretlint/secretlint-rule-aws" should be a boolean, but it is string.
```

## Command line users

### `--secretlintrc` names exactly one file

`--secretlintrc <path>` is resolved from the current directory.
Secretlint no longer looks for the file in the parent directories and no longer adds an extension.
A missing file fails with `secretlint config file is not found: <path>` and exit status 2.

```sh
# v13: found .secretlintrc.json in a parent directory, or added an extension
secretlint "**/*" --secretlintrc .secretlintrc
# v14: write the path of the file
secretlint "**/*" --secretlintrc ../.secretlintrc.json
```

### `--secretlintignore` is a path to an extra ignore file

- `--secretlintignore <path>` is a path from the current directory. Its rules are matched from the current directory, like `core.excludesFile` of Git.
- The file is read **in addition** to `.secretlintignore`. `.secretlintignore` in each directory is always read.
- A missing file prints `secretlint: ignore file not found: <path>` to stderr, and the lint continues.

In v13, the value was used as a file name to look for in each directory, so a path such as `config/ignore` was not read.

### The sources of ignore rules are combined

The built-in rules (such as `**/node_modules`), `.gitignore` files, `.secretlintignore` files, and the file of `--secretlintignore` each decide by themselves with the rules of `.gitignore`.
A file is ignored if any of them ignores it.

A `!` rule re-includes only what the same kind of file ignores. For example, `!secret.txt` in `.gitignore` does not bring back `secret.txt` that `.secretlintignore` ignores.
To lint the files that `.gitignore` ignores, use `--no-gitignore`.

Ignore files are matched like Git. A few patterns where the old matcher (node-ignore) differs from Git now follow Git, such as `a**/b` and the case of non-ASCII letters.
Ignore files in the directories above the current directory are not read.

### `--profile` prints a summary

`--profile` prints a summary by phase, rule, pattern, and file **instead of** the lint results.
`--profile --format json` prints the summary as JSON.
In v13, it printed a line for each file and each rule call.

## Users of custom formatters and the JSON output

### Results no longer have `sourceContent`

A result is `{ filePath, sourceContentType, messages }`.
`--format json` no longer prints the content of each file.

A formatter that needs the content receives `getSource(filePath)` as part of its second argument.
It returns `undefined` when the content is not available.
Secretlint keeps the content of the text files that have messages.

```js
// v13
export default (results) => results.map((result) => result.sourceContent).join("\n");
// v14
export default (results, { getSource }) => {
    return results.map((result) => getSource?.(result.filePath) ?? "").join("\n");
};
```

## Users of the API

- `configFilePath` in the results of `loadConfig()` and `loadConfigDescriptor()` of `@secretlint/config-loader` is `string | undefined`. It is `undefined` when the default configuration is used, and `isDefault` is `true`.
- `runSecretLint()` and `searchFiles()` of `secretlint` always read `.secretlintignore` in each directory. `ignoreFilePath` is read in addition.
- `createEngine()` of `@secretlint/node` reads and scans files on worker threads when there are many files. The results and their order do not change.
- Code that imported `creator` from an official rule package imports it from `@secretlint/core`.

  ```js
  // v13
  import { creator } from "@secretlint/secretlint-rule-aws";
  // v14
  import { creator } from "@secretlint/core/builtin/rules/aws";
  // the presets
  import { presetRecommend } from "@secretlint/core/builtin";
  ```

## Rule authors

- **Files are linted in any order.** A rule must not keep state between files. The order of the results does not change.
- **`"all"` is removed from `SecretLintRuleContentType`** (TypeScript). Use `["text", "binary"]`. A rule that still declares `"all"` runs for text and binary at runtime.
- **`SecretLintRuleCreator` is a union**, and `create` is optional for a rule that has `patterns`. Code that calls `creator.create(...)` directly needs `creator.create?.(...)`.
- **Rules receive the bytes of the source** as `contentBytes` (`Uint8Array | undefined`) of the `SecretLintSourceCode` given to the `file` handler. A rule does not need `node:fs` to read a binary file.
- **New:** a rule can export declarative `patterns` with `keywords`, and the core runs them only on the files that contain a keyword. See [docs/secretlint-rule.md](../secretlint-rule.md). A rule that has only `patterns` does not run on Secretlint v13.
