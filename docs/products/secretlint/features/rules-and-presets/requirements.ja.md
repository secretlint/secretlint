# ルールとルールプリセット

[English](requirements.md)

## このドキュメントについて

Secretlintは、秘密情報の種類ごとにルールを用意して検出します。ルールはrecommendプリセットとcanaryプリセットにまとめられています。
これらのルールはSecretlint自身に組み込まれているため、パッケージをインストールしなくても、設定ファイルにルールIDを書くだけでルールやプリセットを有効にできます。
このドキュメントでは、組み込みルールとプリセット、ルールの識別方法、プリセットからルールにオプションを渡す方法、組み込みルールの追加方法を説明します。
親のProductは[Secretlint](../../product.ja.md)です。

### スコープ

- 組み込みルールとそのルールID
- パッケージをインストールせずに組み込みルールを使うこと、および同じ名前のパッケージの扱い
- recommendプリセットとcanaryプリセットに含まれるルールと、その登録方法
- プリセット内のルールのオプション、重大度、許可するメッセージ、無効化
- 各ルールのドキュメント
- Secretlintのリポジトリへの組み込みルールの追加と、組み込みルールのテスト

### スコープ外

- 各ルールが何を検出するか。これは各ルールのドキュメントで説明します。
- 設定ファイルのルールIDからルールを解決する方法: [設定の読み込み](../config-loading/requirements.ja.md)
- ルールをnpmパッケージとして作成、テストして使うこと: [カスタムルール](../custom-rules/requirements.ja.md)
- コメントで報告を抑制する機能（`@secretlint/secretlint-rule-filter-comments`の動作）。これは「コメントによる無視」の機能に含まれ、まだ書かれていません。

## ユーザーストーリー

### 1つのIDで推奨ルールを有効にする

開発者として、設定ファイルに1つ書くだけで推奨ルールを有効にしたい。ルールを1つずつ列挙しなくて済むからだ。

**受け入れ条件:**

Scenario: 設定ファイルにrecommendプリセットを書くと、プリセットのすべてのルールが動く

- Given: `secretlint`だけがインストールされていて、設定ファイルに`{ "id": "@secretlint/secretlint-rule-preset-recommend" }`がある。
- When: 開発者が、AWSのアクセスキーとGitHubのトークンを含むファイルをlintする。
- Then: 結果に`@secretlint/secretlint-rule-aws`と`@secretlint/secretlint-rule-github`のメッセージがある。

Scenario: 設定ファイルにルールを1つだけ書くと、そのルールだけが動く

- Given: `secretlint`だけがインストールされていて、設定ファイルには`{ "id": "@secretlint/secretlint-rule-aws" }`だけがある。
- When: 開発者が、AWSのアクセスキーとGitHubのトークンを含むファイルをlintする。
- Then: 結果に`@secretlint/secretlint-rule-aws`のメッセージがあり、`@secretlint/secretlint-rule-github`のメッセージはない。

### ルールのパッケージを入れた設定をそのまま使い続ける

ドキュメントに従ってプリセットのパッケージをインストールした開発者として、設定と`package.json`をそのまま使い続けたい。Secretlintを更新するときに何も変えなくて済むからだ。

**受け入れ条件:**

Scenario: 古いプリセットのパッケージが入っていても、Secretlintに組み込まれたプリセットが動く

- Given: `package.json`に`secretlint`と古いバージョンの`@secretlint/secretlint-rule-preset-recommend`があり、設定ファイルにrecommendプリセットがある。
- When: 開発者が、新しいSecretlintで追加されたルールが検出する秘密情報を含むファイルをlintする。
- Then: インストールしたパッケージではなく、インストールしたSecretlintのプリセットが動くため、結果にそのルールのメッセージがある。

Scenario: コードがパッケージからルールをimportすると、組み込みルールと同じものが得られる

- Given: プログラムが、`@secretlint/core`と同じバージョンの`@secretlint/secretlint-rule-aws`から`creator`をimportしている。
- When: プログラムがそのcreatorを`@secretlint/core`に渡して、AWSのアクセスキーを含むファイルをlintする。
- Then: 結果は組み込みルール`@secretlint/secretlint-rule-aws`の結果と同じになる。

### プリセット内のルールを設定する

開発者として、プリセット内のルールのオプションや重大度を設定したり、ルールを無効にしたりしたい。プリセットを使ったまま、リポジトリでの誤検知を減らせるからだ。

**受け入れ条件:**

Scenario: プリセットの項目でルールのオプションを指定すると、そのルールはそのオプションを使う

- Given: 設定ファイルのrecommendプリセットに`"rules": [{ "id": "@secretlint/secretlint-rule-aws", "options": { "allows": ["<そのキー>"] } }]`がある。
- When: 開発者が、そのAWSアクセスキーを含むファイルをlintする。
- Then: 結果に、そのキーについての`@secretlint/secretlint-rule-aws`のメッセージはない。

Scenario: プリセットの項目でルールの重大度を指定すると、そのルールのメッセージはその重大度になる

- Given: 設定ファイルのrecommendプリセットに`"rules": [{ "id": "@secretlint/secretlint-rule-github", "severity": "warning" }]`がある。
- When: 開発者が、GitHubのトークンを含むファイルをlintする。
- Then: `@secretlint/secretlint-rule-github`のメッセージの重大度は`warning`になり、このメッセージが原因でコマンドが失敗することはない。

Scenario: プリセットの項目でルールを無効にしても、ほかのルールは動く

- Given: 設定ファイルのrecommendプリセットに`"rules": [{ "id": "@secretlint/secretlint-rule-github", "disabled": true }]`がある。
- When: 開発者が、AWSのアクセスキーとGitHubのトークンを含むファイルをlintする。
- Then: 結果に`@secretlint/secretlint-rule-aws`のメッセージがあり、`@secretlint/secretlint-rule-github`のメッセージはない。

Scenario: 同じルールをプリセットと単独の両方に書くと、読み込みに失敗する

- Given: 設定ファイルにrecommendプリセットと`{ "id": "@secretlint/secretlint-rule-aws" }`がある。
- When: 開発者がSecretlintを実行する。
- Then: Secretlintは`@secretlint/secretlint-rule-aws`がすでに登録されているというエラーで停止し、どのファイルもlintされない。

### ルールの一部をオプションで有効にする

開発者として、標準では無効になっているルールの一部は、オプションで有効にするまで処理時間がかからないようにしたい。使っていない検査のせいでlintが遅くならないからだ。

**受け入れ条件:**

Scenario: オプションを指定しないと、ルールのその部分はlintに含まれない

- Given: 設定ファイルに、オプションなしの`{ "id": "@secretlint/secretlint-rule-aws" }`がある。
- When: 開発者が、AWSのアクセスキーIDとシークレットアクセスキーを含むファイルをlintする。
- Then: 結果にはシークレットアクセスキーのメッセージがあり、アクセスキーIDのメッセージはない。Secretlintは、そのファイルからアクセスキーIDを探さない。

Scenario: オプションがtrueだと、ルールのその部分が報告する

- Given: 設定ファイルに`{ "id": "@secretlint/secretlint-rule-aws", "options": { "enableIDScanRule": true } }`がある。
- When: 開発者が、同じファイルをlintする。
- Then: 結果には、アクセスキーIDのメッセージとシークレットアクセスキーのメッセージがある。

Scenario: オプションがbooleanではないと、Secretlintは停止する

- Given: 設定ファイルに`{ "id": "@secretlint/secretlint-rule-aws", "options": { "enableIDScanRule": "true" } }`がある。
- When: 開発者がSecretlintを実行する。
- Then: Secretlintは、`@secretlint/secretlint-rule-aws`のオプション`enableIDScanRule`はbooleanでなければならないというエラーで停止し、どのファイルもlintしない。

### lintを遅くせずに自分のパターンを書く

開発者として、`@secretlint/secretlint-rule-pattern`で自分のシークレットのパターンを追加し、それを組み込みルールのパターンと同じ程度の負荷で動かしたいです。自分のパターンや、`secretlint --init`がパターンなしで追加した設定のせいで、すべてのファイルでルールが動かないようにするためです。

**受け入れ条件:**

シナリオ: パターンルールにパターンがないとき、lintの対象にならない

- 前提: 設定ファイルに、推奨プリセットと、`secretlint --init`が書くとおりオプションなしの`{ "id": "@secretlint/secretlint-rule-pattern" }`があります。
- 操作: 開発者が、ほとんどのファイルにどのルールのキーワードもないリポジトリをlintします。
- 結果: 結果は推奨プリセットだけのときと同じで、Secretlintはパターンルールのためだけにファイルを文字列として読みません。

シナリオ: パターンに`keywords`があるとき、そのどれかを含むファイルでだけ実行する

- 前提: パターンルールに`{ "name": "internal token", "patterns": ["/itk_[a-z0-9]{32}/"], "keywords": ["itk_"] }`があります。
- 操作: 開発者が、`itk_`の後に32文字が続くファイルと、`itk_`を含まないファイルをlintします。
- 結果: 1つ目のファイルにパターンルールのメッセージがあり、2つ目のファイルではパターンを実行しません。

シナリオ: パターンに`keywords`がないとき、Secretlintがパターンからキーワードを見つける

- 前提: パターンルールに、`keywords`のない`{ "name": "password", "patterns": ["/password\\s*=\\s*\\S+/i"] }`があります。
- 操作: 開発者が、`PASSWORD = hunter2`を含むファイルと、`password`という語を含まないファイルをlintします。
- 結果: 1つ目のファイルにパターンルールのメッセージがあり、2つ目のファイルではパターンを実行しません。

シナリオ: パターンからキーワードが見つからないとき、そのパターンはすべてのファイルで実行する

- 前提: パターンルールに、`keywords`のない`{ "name": "hex", "patterns": ["/[0-9a-f]{64}/"] }`があります。
- 操作: 開発者が`--profile`を付けてリポジトリをlintします。
- 結果: パターンはこれまでと同じように報告し、プロファイルにはこのパターンが`hex (no keywords)`と表示されます。

### 新しいルールを早めに試す

開発者として、次のメジャーリリースでrecommendプリセットに入る可能性があるルールを使いたい。推奨になる前に、自分のリポジトリで確認できるからだ。

**受け入れ条件:**

Scenario: 設定ファイルにcanaryプリセットを書くと、canaryプリセットのルールが動く

- Given: `secretlint`だけがインストールされていて、設定ファイルに`{ "id": "@secretlint/secretlint-rule-preset-canary" }`がある。
- When: 開発者が、canaryプリセットのルールが検出する秘密情報を含むファイルをlintする。
- Then: 結果にそのルールのメッセージがある。

### 値が報告された理由を読む

開発者として、ルールがその値を報告した理由を読みたい。それが秘密情報なのか誤検知なのかを判断できるからだ。

**受け入れ条件:**

Scenario: ルールが報告したメッセージには、ルールのドキュメントへのリンクがある

- Given: ドキュメントのあるルールがメッセージを報告する。
- When: 開発者が結果を読む。
- Then: メッセージに、ルールのドキュメントとメッセージIDを指すURLがある。

### Secretlintのリポジトリに組み込みルールを追加する

ルールの作者として、npmパッケージを作らずに、新しい種類の秘密情報のルールをSecretlintに追加したい。npmで新しいパッケージを設定しなくても、ルールをリリースできるからだ。

**受け入れ条件:**

Scenario: ルールを生成すると、組み込みルールのファイルが作られる

- Given: ルールの作者がSecretlintのリポジトリで作業している。
- When: ルールの作者が`pnpm run gen:rule`を実行し、名前に`example`を入力する。
- Then: ルールのコード、README、テストケース`ng.secret`と`ok.valid`が`@secretlint/core`の中に作られ、新しいパッケージのディレクトリは作られない。

Scenario: 組み込みルールとして登録すると、ルールIDで使える

- Given: ルール`example`が組み込みルールとして登録され、canaryプリセットに追加されている。
- When: 開発者が、パッケージをインストールせずに`{ "id": "@secretlint/secretlint-rule-example" }`またはcanaryプリセットを使ってlintする。
- Then: ルール`@secretlint/secretlint-rule-example`が動く。

Scenario: Secretlintのテストを実行すると、すべての組み込みルールのスナップショットテストが動く

- Given: 各組み込みルールのスナップショットのテストケースのディレクトリが`@secretlint/core`の中にある。
- When: ルールの作者が`@secretlint/core`のテストを実行する。
- Then: 各テストケースは、キーワードとスコープの確認も含めて、`@secretlint/tester`がカスタムルールを確認するのと同じ方法で確認される。スナップショットのディレクトリがない組み込みルールがあると、テストは失敗する。

### 接頭辞の短い秘密情報のルールを追加する

ルールの作者として、パターンのキーワードの後ろに何が続くかを書けるようにしたい。接頭辞が短い、またはありふれたキーのルールでもlintが遅くならず、キーの一部ではないキーワードを使わずに済むからだ。

**受け入れ条件:**

Scenario: パターンがガード付きキーワードを宣言しても、ルールは同じ秘密情報を報告する

- Given: パターンに正規表現`/00[A-Za-z0-9_-]{40}/`があり、キーワードにガード付きキーワード`{ keyword: "00", after: "[A-Za-z0-9_-]{40}" }`がある。
- When: そのようなキーを含むファイルをlintする。
- Then: ルールは、キーワード`00`を使ったときと同じようにキーを報告する。

Scenario: ガード付きキーワードのガードがサポートしていない書き方だと、lintはエラーで停止する

- Given: パターンに、Secretlintがサポートしていない構文を使ったガード付きキーワード`{ keyword: "00", after: "[^ ]{40}" }`がある。
- When: 開発者がそのルールでlintする。
- Then: Secretlintはそのルールとガード付きキーワードを示すエラーで停止し、どのファイルもlintしない。

## 機能要件

### ルール

**概要:** 各ルールは、1つの種類の秘密情報を検出するか、ほかのルールの報告を絞り込みます。

**入力:** ファイルの内容と、ルールのオプション。

**出力:** ルールID、メッセージID、範囲、重大度、ドキュメントへのリンクを持つメッセージ。

#### 適用する条件

##### ルールID

各組み込みルールのルールIDは`@secretlint/secretlint-rule-<name>`で、これは同じ名前のnpmパッケージの名前でもあります。
ルールIDは、設定ファイルとメッセージの`ruleId`で使われます。
`@secretlint/aws`のような短い形でも、組み込みルールを指定できます。

##### 提供するルール

組み込みルールは、recommendプリセットのルール、`@secretlint/secretlint-rule-pattern`（ユーザー定義のパターン）、`@secretlint/secretlint-rule-azure`です。
組み込みのプリセットは、recommendプリセットとcanaryプリセットです。
プリセットに入っていないルールは、そのルールIDを書いて使います。

Secretlintは、`@secretlint/secretlint-rule-no-dotenv`、`@secretlint/secretlint-rule-no-homedir`、`@secretlint/secretlint-rule-no-k8s-kind-secret`、`@secretlint/secretlint-rule-secp256k1-privatekey`もカスタムルールとして公開しています。これらは[カスタムルール](../custom-rules/requirements.ja.md)と同じく、パッケージをインストールして使います。

##### インストール

組み込みのルールやプリセットは、npm、Dockerイメージ、単一実行ファイル、quick startのどの方法で実行しても、パッケージをインストールせずに使えます。
同じ名前のパッケージがインストールされていても組み込みルールが使われ、そのパッケージは読み込まれません。そのため、ルールのバージョンは常にインストールしたSecretlintのバージョンと一致します。

##### 同じ名前のパッケージ

組み込みルールのパッケージ`@secretlint/secretlint-rule-<name>`と2つのプリセットのパッケージは、引き続き公開されます。どのパッケージも同じバージョンの組み込みルールと同じものをexportするため、これらから`creator`をimportしているコードはそのまま動きます。
これらのパッケージの非推奨化は、別の変更で扱います。

##### ブラウザ

組み込みルールは、Node.jsのモジュールなしにブラウザでも読み込んで実行できます。`.p12`ファイルを扱うGCPルールのように、バイナリの内容を確認するルールは、呼び出し側がソースと一緒に渡すバイト列を使い、ファイルは読み込みません。

##### オプションで有効・無効が切り替わるパターン

ルールは、オプションを指定したときだけ報告するパターンを持てます。たとえば、それだけでは秘密情報ではないIDを探すパターンです。
ルールはこれをデータとして書きます。パターンに、オプションを参照する条件を書きます。有効かどうかをルール自身のコードで判定することはしません。
オプションを読んで、パターンをlintに含めるかどうかを決めるのはSecretlintです。そのため、この判断はファイルを読む前に済み、どのルールでも同じ基準になり、どのオプションがどのパターンを切り替えるのかをSecretlintが把握できます。

- 条件は、ルールのbooleanのオプションを`options.<名前>`と書いて参照します。前に`!`を付けることもできます。`options.<名前>`と書くと、オプションが`true`のときだけパターンがlintに含まれます。`!options.<名前>`と書くと、オプションが`true`でなければパターンがlintに含まれます。
- 条件には、値がどこから来るのか（`options.`）を書きます。あとでルールのオプション以外の値を条件で参照できるようにするときに、すでにある条件の意味を変えずに済むからです。
- 指定されていないオプションは`false`として扱います。
- lintに含まれないパターンには処理時間がかかりません。Secretlintはそのキーワードを探さず、パターンも実行しません。
- 条件を書いていないパターンは、常にlintに含まれます。
- 「有効にする」と「無効にする」は、この条件1つで書きます。オプションで無効になるパターンのための、別のプロパティはありません。
- オプションは、そのルールのbooleanのオプションでなければなりません。TypeScriptでは、ルールのbooleanのオプションではない名前を書くと型エラーになります。
- 条件は、CELのような式言語のごく小さな部分集合で、オプションの参照と`!`だけです。`&&`、`||`、`==`などのほかの演算子はサポートしません。必要になったときは条件の書き方に追加します。それを知らないSecretlintは、条件を別の意味に読むのではなく、エラーで停止します。

##### ユーザー定義のパターン

`@secretlint/secretlint-rule-pattern`は、設定ファイルがオプションで定義したパターンに一致した箇所を報告します。
Secretlintはこのオプションを、組み込みルールが宣言するパターンと同じようにパターンとして読みます。パターンはデータで、Secretlintがそれを実行します。

- `patterns`、`pattern`、`filePathGlobs`のどれもないエントリは、これまでどおり許可しません。オプションにエントリが1つもないとき、ルールはlintの対象になりません。キーワードを追加せず、どのファイルでも実行しません。
- エントリは`keywords`(ASCII文字列のリスト)を持てます。パターンは、そのどれかを含むファイルでだけ実行します。照合ではASCIIの大文字と小文字を区別しません。パターンのすべての一致はキーワードのどれかを含む必要があり、含まない一致は報告しません。ASCII以外の文字を含むキーワードや空のキーワードはエラーです。`keywords: []`は、パターンをすべてのファイルで実行します。
- エントリに`keywords`がないとき、Secretlintは、パターンのすべての一致が必ず含む文字列を見つけ、それをそのパターンのキーワードとして使います。確実なときだけ使います。パターンに解釈できない部分があるときは、そのパターンはキーワードを持たず、これまでどおりすべてのファイルで実行します。
- キーワードは、パターンのASCII文字からだけ見つけます。フラグ`i`を持つパターンは、`k`に対するケルビン記号(U+212A)のように、ASCII文字に畳み込まれるASCII以外の文字にも一致します。ファイルにASCIIのキーワードがないとき、こうした一致は報告しません。Secretlintはリンターで、検出漏れをなくすことより誤検知をなくすことを優先するので、これを受け入れます。
- `filePathGlobs`だけのエントリは、キーワードを使わず、内容と照合せずに、パスが一致したファイルを報告します。
- ルールID、メッセージID `PATTERN`、メッセージ、エントリの`allows`と`filePathGlobs`の意味は変えません。
- `--profile`は、ルールの各パターンを名前で表示し、すべてのファイルで実行するパターンには名前の後に` (no keywords)`を付けます。

##### ガード付きキーワード

パターンは、ガード付きキーワードを宣言できます。ガード付きキーワードは、ガード（キーワードの後ろに続く文字についての条件）を持つキーワードです。Secretlintにガードがある理由と、ガードが保つことは、[秘密情報の検査](../secret-scanning/requirements.ja.md)に書いています。
ルールは、キーワードと同じようにガードをデータとして書き、Secretlintがそれを確かめます。

- ガード付きキーワードは、パターンのキーワードの要素の1つです。要素は、これまでどおりの文字列か、ガード付きキーワードを表すオブジェクトです。文字列の意味はこれまでと変わりません。文字列を新しい意味で読むことはありません。
- オブジェクトは、キーワードと、その後ろに続くもの（文字の集合と数）を持ちます。たとえば`{ keyword: "00", after: "[A-Za-z0-9_-]{40}" }`は、キーワード`00`と、その後ろに英字、数字、`_`、`-`が40文字以上続くことを表します。
- オブジェクトのキーワードは、文字列のキーワードと同じように書きます。特別な意味を持つ文字はありません。
- 後ろに続くものは、正規表現の一部として書き、その部分と同じ意味になります。そのため、ルールの作者は、パターンの正規表現からキーワードの後ろの部分を写して書けます。
- その構文は、正規表現の構文のごく小さな部分集合です。ASCII文字の集合1つと、数1つだけです。数は、少なくとも何文字続くかを表します。`{32,40}`のように上限のある数も書けますが、意味は`{32,}`と同じです。もっと長い文字の並びの先頭に一致する正規表現が表すことも、同じだからです。
- `^`を使った集合、グループ、2つ目の集合などのほかの構文はサポートしません。オブジェクトにほかのプロパティもありません。必要になったときは、構文に追加するか、新しい名前のプロパティとして追加します。それを知らないSecretlintが、ガードを別の意味に読むことはありません。
- ガード付きキーワードは、既定では、キーワードも集合もASCIIの英字の大文字と小文字を区別しません。パターンがキーワードの大文字と小文字を区別すると宣言したときは、どちらも区別します。
- パターンのすべての一致は、キーワードのどれかを含まなければなりません。ガード付きキーワードの場合は、ガードを満たす文字も含まなければなりません。これはキーワードに対する責任と同じで、ルールのテストが確かめます。[カスタムルール](../custom-rules/requirements.ja.md)を参照してください。
- パターンのキーワードには、文字列とオブジェクトを一緒に書けます。どれかが見つかった場所でパターンを実行します。
- ガード付きキーワードは、「line」スコープに必要なキーワードとして数えます。
- ガードはパターンのためのものです。パターンを持たないルールの`meta.keywords`にガードはありません。
- 利用者もガード付きキーワードを書けます。オブジェクトはデータなので設定ファイルに書けます。`@secretlint/secretlint-rule-pattern`のエントリの`keywords`にも、同じ要素を書けます。「ユーザー定義のパターン」を参照してください。
- ガード付きキーワードを使うカスタムルールは、ガード付きキーワードを知らないSecretlintでも同じ結果になります。そのようなSecretlintは、そのパターンのキーワードを使わず、パターンを内容全体に実行するので、遅くなるだけです。

##### ドキュメント

各ルールには、値を報告する理由、メッセージ、オプションを説明するREADMEがあります。

#### 例外ケースでの振る舞い

##### パターンの条件がサポートしていない書き方である

パターンの条件が文字列ではないとき、または`options.<名前>`でも`!options.<名前>`でもない文字列のとき、Secretlintはそのルールと条件を示すエラーで停止し、どのファイルもlintしません。

##### 条件が参照するオプションの値がbooleanではない

条件が参照するオプションに、文字列の`"true"`のような`true`でも`false`でもない値が指定されているとき、Secretlintはそのルールとオプションを示すエラーで停止し、どのファイルもlintしません。Secretlintは、ほかの値を`true`や`false`に読み替えません。

##### ユーザー定義のパターンのキーワードが正しくない

`@secretlint/secretlint-rule-pattern`のエントリの`keywords`が、空でないASCII文字列とガード付きキーワードのリストではないとき、Secretlintはそのエントリを示すエラーで止まり、どのファイルもlintしません。

##### ガード付きキーワードがサポートしていない書き方である

キーワードの要素がオブジェクトで、キーワードとガードを文字列として持たないとき、ほかのプロパティを持つとき、ASCIIでない文字を含むとき、またはガードが構文のサポートしていない書き方のとき、Secretlintはそのルールと要素を示すエラーで停止し、どのファイルもlintしません。
`*`、`?`、`{0,}`のように、ガードが常に成り立ってしまう数もエラーです。
Secretlintは、代わりにガードなしでパターンを実行することはしません。ガードの書き間違いは、遅いlintとしてではなく、最初のlintで見つかります。

### ルールプリセット

**概要:** プリセットは、決められたルールの一覧を登録するルールです。

**入力:** 設定ファイルのプリセットの項目と、その中に書くルールごとの設定の一覧`rules`。

**出力:** プリセットの各ルールが、個別に書いた場合と同じように、プリセットの項目で指定したオプションで動きます。

#### 適用する条件

##### recommendプリセット

`@secretlint/secretlint-rule-preset-recommend`には、`@secretlint/secretlint-rule-filter-comments`を含む28個のルールが入っています。
recommendプリセットにルールを追加すると、Secretlintが初期設定で報告するエラーが増えるため、追加はメジャーリリースで行います。

##### canaryプリセット

`@secretlint/secretlint-rule-preset-canary`には、recommendプリセットに入る予定のルールが入っています。
Semantic Versioningには従わず、マイナーリリースでもルールが追加されます。
現在は、recommendプリセットと同じルールが入っています。

##### プリセット内のルール

プリセットの項目の`rules`にある各項目は、ルールIDでルールと対応づけられます。
プリセットに入っていないルールの項目と同じように、そのルールの`options`、`severity`、`allowMessageIds`、`disabled`を設定できます。
`disabled: true`を指定したルールは動きません。
項目のないルールは、既定のオプションで動きます。

#### 例外ケースでの振る舞い

##### 同じルールIDが2回登録される

プリセットと単独の項目の両方に書くなどして同じルールIDが2回登録されると、SecretlintはそのルールIDを含むエラーで停止します。

### 組み込みルールの追加

**概要:** 組み込みルールは、新しいnpmパッケージとしてではなく、Secretlintのファイルとして追加します。

**入力:** ルールの名前、コード、README、スナップショットのテストケース。

**出力:** パッケージをインストールせずに`@secretlint/secretlint-rule-<name>`で使えるルール。

#### 適用する条件

##### 登録

新しいルールは組み込みルールとして登録し、canaryプリセットに追加します。recommendプリセットへの追加はメジャーリリースで行います。

##### テスト

組み込みルールのスナップショットのテストケースは`@secretlint/core`にあり、`@secretlint/core`のテストで実行します。プリセットのテストでは、プリセットに含まれるルールのテストケースをプリセットとして実行し、`ok.*`のケースはプリセットのどのルールにも報告されてはいけません。
テストケースの構成は`@secretlint/tester`と同じで、テストケースの設定ファイルに書くルールIDは組み込みルールを指します。

## データ要件

### 必要なデータ

- **ルールID:** 設定ファイルとメッセージで、ルールやプリセットを識別する名前。
- **プリセットのルール一覧:** プリセットが登録するルールを、決まった順に並べたもの。
- **パターンの条件:** ルールのパターンをlintに含めるかどうかを決める、booleanのオプションの参照（`options.<名前>`）。前に`!`を付けることもできる。

### データ間の関係

プリセットはルールを含みます。メッセージは、それを報告したルールをルールIDで示します。

### 個人情報

なし。ルールはファイルの内容を読み、報告する値が秘密情報であることもあります。その値を隠すことは「結果の秘密情報のマスク」機能で扱います。

## 依存する外部サービス

- **npm registry**
  - **関連するユーザーストーリー:** 1つのIDで推奨ルールを有効にする、ルールのパッケージを入れた設定をそのまま使い続ける、新しいルールを早めに試す
  - **依存する理由:** 組み込みルールを含むSecretlintと、同じ名前のパッケージは、npmパッケージとして配布されます。
  - **契約・利用上の判断:** npm registryの公開パッケージで、無料です。

## セキュリティ上の留意事項

組み込みルールは、Secretlintから渡された内容だけを読み、ネットワークは使いません。

## 未決事項

- パターンを持たないルールの`meta.keywords`にもガードを付けられるようにすべきか。いまは必要とするルールがありません。
- どのルールが最初にガード付きキーワードを使うか。recommendプリセットのキーワードは長く、ガードを付けても何も変わりません。
