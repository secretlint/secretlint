# 性能プロファイルの設計

[English](design.md)

## このドキュメントについて

このドキュメントは、[Secretlint](../../product.ja.md)の[性能プロファイル](requirements.ja.md)をどう実現しているかを説明する。

### 対象読者

計測する箇所を追加する人、要約を変更する人、ファイルごとやパターンごとに動くコードを変更する人とエージェント。

### 前提知識

この機能のRequirements。検査の流れ。コマンドがファイルを探し、エンジンが各ファイルを読み、コアが内容を走査して全ルールのキーワードを探し、パターンとルールを実行する。

### このドキュメントで扱わないこと

キーワード走査とパターンの仕組み。フォーマッターが検査結果を出力する方法。

## 実装方針

### 合計値を保持する1つの共有プロファイラ

`@secretlint/profiler`はプロファイラのインスタンスを1つ公開し、すべてのパッケージがそこに記録する。コマンド、エンジン、設定ローダー、コアの間でプロファイラを受け渡すことはしない。

プロファイラは、種類とIDの組ごとに合計値を保持する。合計値は、回数、合計時間、最長時間である。個々の記録は保持しない。
1回の実行では、ファイルごと、パターンの実行ごとに記録が発生する。個々の記録を保持するとファイル数に比例して増え、記録のたびにオブジェクトを作ると、その時間がプロファイル自体に現れてしまう。

プロファイラは既定で無効である。コマンドは`--profile`で、エンジンは`profile: true`でプロファイラを有効にする。

### 2つの記録方法

- **開始と終了の印の組**は、設定の読み込みのように、1回または数回だけ動く段階に使う。コードは種類を付けて開始と終了に印を付け、プロファイラは種類とIDから開始を見つける。
- **開始時刻と記録**は、ファイルごとやパターンごとに動くコード、または終わる前に再び動きうるコードに使う。コードは時計を読み、処理を行い、種類、ID、開始時刻を記録する。呼び出しごとに開始時刻を持つので、重なって動く検査もすべて記録される。

### プロファイラが無効なときのコスト

ファイルごとやパターンごとに動くコードは、時計を読んだり何かを作ったりする前に、プロファイラが有効かどうかを確認する。無効なプロファイラがそこで払うコストは、この真偽値の確認だけである。
パターンのIDは文字列で、実行のたびではなく、検査計画を作るときに1回だけ作る。
印の組は、印ごとにオブジェクトを作るので、1回の実行で数回しか動かない箇所にだけ使う。

ファイルごとやパターンごとに動くコードへ計測箇所を追加する変更では、Requirementsが述べるとおり、変更の前後で`--profile`を付けない実行を比べる。

### 計測するもの

| 種類 | ID | 記録するパッケージ | 意味 |
| --- | --- | --- | --- |
| `secretlint>cli` | | コマンド | コマンド全体 |
| `secretlint>search-files` | | コマンド | 検査するファイルを探す |
| `@node>load-config` | | エンジン | 設定を読み込む。`@config-loader>*`の種類を含む |
| `@node>execute` | | エンジン | ファイルを検査し、結果を整形する |
| `@node>files` | | エンジン | その実行のファイルの数。時間は持たない |
| `@node>keyword-scan` | | エンジン | 検査の前に、メインスレッドとワーカースレッドでファイルを走査してルールのキーワードを探す |
| `@node>keyword-scan-thread` | スレッドの名前 | エンジン | `@node>keyword-scan`の中での1つのスレッドの時間とファイル数。ワーカーが測り、エンジンが`addTotal()`で足す |
| `@node>read-file` | | エンジン | ファイルを読む |
| `@node>format` | | エンジン | 結果を整形する |
| `@core>lint` | ファイルパス | コア | 1つの内容を検査する |
| `@core>setup-rules` | | コア | 検査計画を作る。1つの設定につき1回動く |
| `@core>keyword-scan` | | コア | 内容を走査して全ルールのキーワードを探す |
| `@core>line-check` | | コア | キーワードのある行をテストする。`@core>pattern-line-test`を含む |
| `@core>pattern-line-test` | パターンのID | コア | 1つの行を1つのパターンでテストする |
| `@core>pattern` | パターンのID | コア | パターンを実行し、マッチを報告する |
| `@core>pattern-match` | パターンのID | コア | マッチ数。時間は持たない |

パターンのIDは、`{ルールID}#{ルール内でのパターンの番号} {正規表現}`である。パターンには名前がないので、読む人は正規表現でパターンを見分ける。
ルールIDは、設定ファイルに書かれたIDではなく、ルール自身のIDである。そのため、設定ファイルで短いIDを使っても同じ行になる。

キーワード走査のためだけに内容をデコードする場合は、時計を読む前にデコードする。これにより、走査の時間にデコードの時間は含まれない。

### 要約

コマンドは検査が終わったときに合計値から要約を作り、フォーマッターの出力の代わりに、コマンドの出力として返す。フォーマッターは実行するが、その出力は`--output`にだけ使う。
要約を作る処理と、テキストに整形する処理は分かれている。前者は`--format json`が出力するオブジェクトを作り、後者は表を作る。
段階の順序と深さは、コマンドが持つ固定の一覧で決まる。一覧にない種類は段階ではない。

テキストでは、表のすべてのセルから端末の制御シーケンスと制御文字を取り除く。JSONではエスケープされる。

## アーキテクチャ・シーケンス図

図は不要である。各パッケージが共有プロファイラに記録し、コマンドが最後に1回だけ合計値を読む。

## データモデル・ER 図

合計値は`{ type, id, count, duration, maxDuration }`である。対象のない種類では`id`は`undefined`になる。時間はミリ秒である。

要約は`{ total, files, phases, rules, patterns, slowestFiles }`である。

- `phases`: `{ name, depth, duration, percent, count }`
- `rules`: `{ ruleId, duration, files }`
- `patterns`: `{ ruleId, index, pattern, duration, runDuration, runs, matches, lineTestDuration, lineTests }`。`duration`は`runDuration + lineTestDuration`である
- `slowestFiles`: `{ filePath, duration }`

## API・インターフェース

- コマンド: `--profile`。`--format json`でJSONの要約を選び、それ以外の値ではテキストを選ぶ。
- エンジン: `createEngine()`の`profile`オプション。`true`でプロファイラを有効にし、`false`で無効にする。オプションがなければプロファイラの状態を変えない。
- プロファイラ(`@secretlint/profiler`): 読む側は`secretLintProfiler.setEnabled()`、`isEnabled`、`getStats()`を使う。記録するSecretlintのパッケージは`mark()`、`now()`、`record()`、`count()`を使う。

なし。

## データの取り扱い設計

合計値はプロセスのメモリにある。プロファイラを無効にすると消える。ファイルには何も書かない。

## セキュリティ上の留意事項

要約は、ファイルパス、ルールID、正規表現を含む。Requirementsが述べるとおり、テキストではこれらから端末の制御シーケンスと制御文字を取り除く。
プロファイラは、ファイルの内容もマッチした値も受け取らない。

## 検討した代替手段

### `performance.mark()`と`PerformanceObserver`

Performance APIで各処理の開始と終了に印を付け、オブザーバーで計測結果を集める方法である。
以前の設計はこの方法だった。ファイルごとに印とエントリーを作るため、7,220ファイルで`--profile`付きの実行が41%遅くなり、出力はファイルごとに1行になっていた。そのため採用しなかった。

### 個々の記録を保持し、出力時に集計する

プロファイラがすべての記録の一覧を保持し、コマンドがそれを集計する方法である。
一覧がファイル数とパターンの実行回数に比例して増え、要約には合計値しか必要ないため、採用しなかった。

### キーワード走査の時間をルールに割り振る

共有する走査の時間を、キーワードの数に応じて各ルールに加える方法である。
走査は全キーワードをまとめて1回で行うもので、その時間は1つのルールのキーワード数に比例して変わらない。割り振った数値はルールのコストに見えるが、そのルールを外してもその時間は減らない。そのため採用しなかった。

### 要約を検査結果と一緒に出力する

標準出力で検査結果の前に要約を出す方法や、要約を標準エラーに出す方法なら、検査結果も残る。
`--profile`を付けた実行はプロファイルを見るためのものである。1つの出力に2つの文書が並ぶとJSONとして解析できず、両方を必要とする読み手もいない。そのため採用しなかった。

### 要約の形式を選ぶ別のオプションを持つ

`--profile=json`のようなオプションなら、`--format`は検査結果のためだけに残る。
`--profile`では検査結果を出力しないので、そこでは`--format`にほかの意味がない。形式を選ぶオプションは2つより1つのほうが単純である。そのため採用しなかった。

### JavaScriptエンジンのCPUプロファイルだけを使う

`node --cpu-prof`とその要約ツールで、この機能を置き換える方法である。
ルールはデータであり、実行するのはコアである。そのためCPUプロファイルにはコアの関数が現れ、ルールやパターンは現れない。これだけを手段とすることは採用しなかった。段階の中を調べる道具としては引き続き使う。
